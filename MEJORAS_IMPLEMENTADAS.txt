2. VALIDACIONES MEJORADAS EN CLIENTE
================================================================================

ARCHIVO MODIFICADO: modelos/cliente.py

¿QUÉ CAMBIÓ?
  a) NOMBRE
     ANTES: Solo validaba que no estuviera vacío
     AHORA: Valida que tenga mínimo 3 caracteres después del strip()
     
  b) DOCUMENTO
     ANTES: Solo validaba que fuera numérico
     AHORA: Valida mínimo 5 dígitos (evita números muy cortos)
     
  c) TELÉFONO
     ANTES: Validaba mínimo 7 dígitos
     AHORA: Valida máximo 15 dígitos (estándar E.164 internacional)
     
  d) ENCADENAMIENTO DE EXCEPCIONES
     ANTES: raise ClienteInvalidoError("mensaje")
     AHORA: raise ClienteInvalidoError("...") from e
     RAZÓN: Proporciona mejor contexto para debugging

¿POR QUÉ?
  • Prevenir datos tan cortos que no tengan sentido
  • Cumplir estándares internacionales (E.164 para teléfonos)
  • Usar encadenamiento de excepciones como indica el requisito

NUEVOS MÉTODOS AGREGADOS:
  ```python
  @property
  def historial_reservas(self):
      """Retorna lista de reservas del cliente"""
      return self.__historial_reservas.copy()
  
  def agregar_reserva(self, reserva):
      """Registra una reserva en el historial del cliente"""
      self.__historial_reservas.append(reserva)
  
  def obtener_total_gasto(self):
      """Calcula total gasto del cliente en todas sus reservas"""
      return sum(r.servicio.calcular_costo() for r in self.__historial_reservas)
  ```

3. VALIDACIONES MEJORADAS EN SERVICIO
================================================================================

ARCHIVO MODIFICADO: modelos/servicio.py

¿QUÉ CAMBIÓ?
  a) VALIDACIÓN DE COSTO_BASE
     ANTES: Se asignaba sin validación
     AHORA: Se valida que sea > 0 en el constructor
     
  b) VALIDACIÓN DE DISPONIBLE
     ANTES: No se validaba el tipo
     AHORA: Se verifica que sea booleano (True/False)
     
  c) ENCADENAMIENTO DE EXCEPCIONES
     ANTES: No usaba encadenamiento
     AHORA: raise DatosInvalidosError(...) from e

¿POR QUÉ?
  • Un servicio con costo 0 o negativo no tiene sentido
  • Evitar que 'disponible' sea una cadena "False" en lugar de False
  • Cumplir con el requisito de encadenamiento de excepciones

CÓDIGO NUEVO EN CONSTRUCTOR:
  ```python
  def __init__(self, nombre, costo_base, disponible=True):
      try:
          if costo_base <= 0:
              raise ValueError(
                  f"El costo base debe ser mayor a 0. Costo: {costo_base}"
              )
          if not isinstance(disponible, bool):
              raise ValueError(
                  f"'disponible' debe ser booleano. Recibido: {type(disponible)}"
              )
      except ValueError as e:
          raise DatosInvalidosError(f"Validación falló: {e}") from e
      
      self.nombre = nombre
      self.costo_base = costo_base
      self.disponible = disponible
  ```

4. MEJORAS EN CLASE RESERVA - try/except/else/finally EXPLÍCITO
================================================================================

ARCHIVO MODIFICADO: modelos/reserva.py

¿QUÉ AGREGÓ?
  a) ID ÚNICO POR RESERVA
     Cada reserva tiene un UUID único para trazabilidad
     
  b) FECHA DE CREACIÓN
     Se registra cuándo se creó la reserva
     
  c) HISTORIAL DE CAMBIOS
     Cada cambio de estado se registra con timestamp
     
  d) BLOQUE try/except/else/finally EXPLÍCITO
     En el método procesar_reserva()

¿POR QUÉ?
  El requisito especificaba:
  "Usar bloques try/except, try/except/else, try/except/finally"
  
  Y además:
  "manteniendo la aplicación activa y estable en todo momento"

IMPLEMENTACIÓN DEL FLUJO COMPLETO:
  ```python
  def procesar_reserva(self):
      try:
          # BLOQUE TRY: Intenta validar
          self.validar_datos()
          # Si llegamos aquí sin excepción, va al ELSE
          
      except ServicioNoDisponibleError as e:
          # EXCEPT específico para servicio no disponible
          logger.error(f"Servicio no disponible: {e}")
          raise e
          
      except ReservaError as e:
          # EXCEPT específico para errores de reserva
          logger.error(f"Error en reserva: {e}")
          raise e
          
      except Exception as e:
          # EXCEPT genérico para cualquier otro error
          logger.critical(f"Error inesperado: {e}")
          raise ReservaError("Error interno") from e
          
      else:
          # ELSE: SOLO ejecuta si NO hubo excepción en try
          try:
              self.confirmar()
              costo = self.servicio.calcular_costo()
              print(f"✅ Reserva exitosa: ${costo:,.2f}")
          except Exception as e:
              logger.error(f"Error al confirmar: {e}")
              raise
              
      finally:
          # FINALLY: SIEMPRE ejecuta (limpieza)
          logger.debug(f"Procesamiento completado - Estado: {self.estado}")
  ```

EJEMPLO DE HISTORIAL DE CAMBIOS:
  ```

     - 2026-05-08 10:59:10.947785: None → Pendiente (Creación de reserva)
     - 2026-05-08 10:59:10.948409: Pendiente → Confirmada (Confirmación exitosa)
     - 2026-05-08 10:59:10.956327: Confirmada → Cancelada (Cancelación desde estado Confirmada)
  ```
